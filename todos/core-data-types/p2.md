# P2 findings: core-data-types

- crates/core/src/column.rs:162 | `ColumnBatch::selection_mut()` returns `&mut Bitmap`, so a caller can replace the selection with one of a different length. `len()` (column.rs:140) is the selection length, so a shorter bitmap silently drops rows from `len()`/`to_rows()`, and a longer one makes `to_rows()` panic. Confirmed with a scratch crate: 10 rows with a 4-bit selection gives 4 rows; a 12-bit selection panics with "bit 10 out of range for bitmap of 10". Fix: return a narrow handle (set/get/len/count_ones, not replaceable) so the locked AC-2 call `selection_mut().set(3, false)` still compiles, and add a unit test. | MEDIUM | architecture-strategist (#1), code-quality reviewer (#1, confirmed)

**Resolved:** `selection_mut()` now returns `SelectionMut<'_>`, which offers `set` plus read-only `Deref<Target = Bitmap>` and has no `DerefMut`, so the bitmap cannot be replaced. Covered by the unit test `selection_mut_flips_bits_without_changing_length` and a `compile_fail` doctest (the assignment is rejected with E0594). The locked AC-2 call compiles unchanged.
